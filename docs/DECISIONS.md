# 설계 결정

결정마다 이유를 함께 적습니다. 바꾸려면 이유가 아직 유효한지부터 확인하세요.

## D1. 추천 엔진은 서버에 둔다

- **결정**: 모델 기준표, 점수 규칙, clef-flash 질문, 검수 카탈로그는 Worker에 둡니다. 모드는 화면과 로컬 정보 수집, 적용만 맡습니다.
- **이유**:
  - 플러그인은 설치할 때 소스째 고객 PC에 복사되므로, 클라이언트에 둔 로직은 숨길 수 없습니다.
  - 가격이나 규칙을 바꿔도 고객 업데이트가 필요 없습니다.
- **결과**: Worker가 응답하지 않으면 추천 없이 “현재 모델을 그대로 쓰세요”로 끝납니다(fail open).

## D2. 분류는 clef-flash, 질문 문구는 길게

- **결정**: Cloudflare Workers AI `@cf/cloudflare/clef-flash`로 8개 항목을 묻습니다. 작업 종류, 난이도, 위험, 긴 문맥, 추론, 도구, 비전, 우선 목표입니다. 질문과 보기 설명은 길고 구체적으로 씁니다.
- **이유**: 실측 결과입니다. 짧은 질문으로는 “10만 줄 코드 분석”이 ‘단순, 긴 문맥 0.02’로 나왔습니다. 질문을 다듬고 규모 힌트를 넣자 ‘분석, 복잡(1.95/2), 긴 문맥 0.90’으로 나왔습니다.
- **함께 쓰는 규칙**:
  - 규모 숫자는 규칙으로 뽑아 힌트로 넣습니다(“만 줄”, “페이지”, “GB” 등).
  - clef-flash가 실패하면 키워드 규칙만으로 분류합니다.

## D3. 신뢰도가 낮으면 현재 모델을 유지한다

- **결정**: 전체 신뢰도 = 0.6 × 작업 종류 신뢰도 + 0.4 × 평균(난이도 신뢰도, 위험 신뢰도). 0.35 미만이면 ★최적안을 “현재 설정 유지”로 둡니다.
- **이유**: 실측 결과입니다. “도와줘” 0.06, “음…” 0.11, “어제 그거 다시 해줘” 0.08은 걸러지고, “회의록 요약” 0.43, “레이트 리밋 추가” 0.48은 통과합니다.

## D4. 고위험 작업은 상위 모델을 최적안으로

- **결정**: 위험 점수 1.5/2 이상이면 품질안이 ★최적안이 됩니다. 실행 팁에 리뷰 단계를 넣습니다.
- **이유**: 기획서 요구사항(“위험이 높은 작업에는 검증된 상위 모델을 우선”)입니다.

## D5. 스킬·플러그인 출처는 PluginWorld 하나

- **결정**: 미설치 추천은 PluginWorld API만 씁니다. SkillsMP와 Claude Market은 쓰지 않습니다. 보안 등급 C 이하는 추천하지 않습니다.
- **이유**: 2026-10-10에 세 곳을 직접 호출해 비교했습니다.
  - PluginWorld: 서버 호출 가능(키 없음, IP당 분당 60회). 플러그인·MCP·스킬을 한 API에서 다루고, 품질 점수·보안 등급·라이선스·최근 커밋·설치 명령을 줍니다.
  - SkillsMP: 키 없이는 하루 50회, 스킬만 다룸, 설치 명령 없음.
  - Claude Market: 서버 호출이 봇 체크포인트(429)에 막힘.
- **예비**: PluginWorld가 실패하면 Worker에 내장된 48개 검수 목록을 씁니다.

## D6. 고객사 전용: 조직 키만 받는다

- **결정**: 키 자동 발급(`POST /v1/keys`)은 기본으로 닫혀 있습니다(403). 키는 CSTOKEN이 고객사별로 발급합니다.
- **이유**: 코드는 공개돼 있어도 키 없이는 동작하지 않게 하려는 것입니다. 사용 통제는 저장소 접근이 아니라 API 키로 합니다.
- **되돌리기**: Worker 변수 `FINOPS_KEY_ISSUANCE=open`이면 무료 키(하루 100회)를 다시 발급합니다.

## D7. 이름에는 finops를 넣는다

- **결정**: 사람이 보거나 입력하는 이름에는 모두 `finops`가 들어갑니다.
  - 환경 변수 `CSTOKEN_FINOPS_*`
  - 키 형식 `cst_finops_…`
  - 명령 `/finops`, 패널 id `finops`, 제목 `CSTOKEN FinOps`
  - 주소 `finops.cstoken.net`
- **이유**: CSTOKEN의 하위 도구라는 점을 분명히 하고, 다른 CSTOKEN 제품과 섞이지 않게 하려는 것입니다.

## D8. [적용]은 사람이 누른다

- **결정**: 자동 모드 전환은 하지 않습니다. 진단도 버튼을 눌러야만 실행됩니다(프롬프트마다 자동 진단 안 함).
- **이유**: 기획서 요구사항(“초기에는 추천 후 사용자가 적용하는 구조가 안전”)입니다. 또 평소 프롬프트에 지연이나 비용을 더하지 않으려는 것입니다.
- **방식**: 모델은 `/model`로 바꾸고, effort는 `turn.step` 훅이 유지합니다. 사용자의 영구 설정은 건드리지 않습니다.

## D9. 화면은 결론부터

- **결정**: 패널은 추천 카드 → 다른 선택지 → 근거 → 도구 → 지출 순서로 보여 줍니다.
  - 확률값 대신 단어로 표시합니다(높음·보통·낮음, “필요: 긴 문맥”).
  - 비용은 막대와 “현재보다 $x 절약/추가”로 비교합니다.
  - 입력창 위 줄에는 상태마다 주 동작을 하나만 둡니다.
- **이유**: 첫 버전은 분류 수치가 결론보다 위에 있었고, 비교 기준(현재 모델)도 없었습니다.

## D10. 비용은 정가 기준 추정치

- **결정**: 추천 카드 금액과 원장 지출은 모두 정가 기준입니다.
  - 추천 카드는 캐시를 반영하지 않습니다.
  - 원장은 캐시 읽기·쓰기 단가를 반영합니다.
  - 화면에 “대략치”라고 밝힙니다.
- **이유**: 구독제와 할인은 클라이언트에서 알 수 없습니다. 모델 간 상대 비교에는 정가로 충분합니다.
